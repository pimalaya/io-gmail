# io-http 0.7

The crate moves from io-http 0.6 to 0.7.0, and its dev-dependency io-oauth from 0.5 to 0.6.0, itself on io-http 0.7, so a single io-http resolves in the graph. The lockfile follows io-oauth 0.6 onto rsa 0.10.0 and loses rand and chacha20. The fuzz crate names io-http itself and moves with it. Nothing had to change to compile: the crate hands `HttpRequest` values to `Http11Send::new`, which stays infallible, and it never called `to_http_11_vec`, the event stream parser or the `Display` of `HttpAuthBearer`. tests/gmail.rs compiles unchanged against the JWT bearer client of io-oauth 0.6.

Breaking for consumers all the same: the coroutines take io-http's `HttpAuthBearer` and `GmailSendError::Send` carries its `Http11SendError`, so a consumer moves in step.

Three points of the family audit of 2026-11-13 were left for this bump.

**The token check stays.** io-http 0.7 refuses a header value holding CR, LF or NUL at the first resume of `Http11Send`. `gmail_authorization` refuses any control character when the coroutine is built, which is earlier and wider (a tab, DEL), so it is kept as the first line and the library's is the second.

**The path helper (FAM-11).** `gmail_api_url` is now io-http's `rfc3986::path::http_url_build` under `GMAIL_API_BASE`, its two errors mapped: a refused segment to `GmailSendError::InvalidRequest`, a base that does not parse (which the constant cannot cause) to `ParseUrl`. Every request the scripted tests pin is unchanged. One behaviour moved, and it was a defect: the URL parser strips tabs and line breaks from a pushed segment, so a label id of `.`, tab, `.` passed the dot check and was resolved as `..`, the URL built being `/gmail/v1/users/me/` (`segments_the_url_would_alter_are_refused` failed with exactly that against the previous body), and `Label`, tab, `_1` reached `Label_1`. The helper refuses such a segment. The message of the refusal is now the helper's.

**The memory bound (GMAIL-05).** tests/memory.rs fed the 4 MiB raw message in one piece only, and in one piece the peak is the same on both releases, twice the message (8388910 bytes on 0.6, 8390958 on 0.7): the head reader of the HTTP layer splits the body off the piece it was given. Read by 16 KiB, the size of a read of the std client, the peak was 12557329 bytes on 0.6, three times the message, and is 8388627 on 0.7, twice plus 19 bytes: the HTTP layer holds the body once (4226965 bytes for a response whose body is not kept), and what remains is the body beside the string parsed from it. The test now reads both ways and bounds each at twice the message plus 64 KiB, where the bound was two and a half times.

What the HTTP layer now does under the coroutines, unchanged code: interim 1xx responses are skipped, up to 8; chunk data without its CRLF fails, trailers are read and dropped; a final transfer coding other than `chunked` fails; an HTTP/1.0 response keeps the connection only on the `keep-alive` option. No scripted test pinned any of it.

Capabilities moved: requests (the requirement "An id is one path segment" modified, a tab or a line break is refused), responses (the requirement "The receive buffer is released before the body is parsed" modified, the bound is twice the body).

Verified: `cargo test --all-features` passed (3 unit, 52 integration, 2 doc, the live test ignored and not run), `cargo clippy --all-features --all-targets -- -D warnings` clean, `cargo build --no-default-features` builds, `cargo publish --dry-run` packages against the registry, `cargo fuzz build` builds the `batch` target in the `fuzz` devShell.

Left open:

- No change folder was opened for this bump: the delta is the two requirements above, folded straight into the spec.
- A body answered in several chunks is still held three times: the same raw message in chunks of 64 KiB, read by 16 KiB, peaked at 12615502 bytes on io-http 0.7 (8388610 in a single chunk). The bound of the test holds for an answer carrying its length, and the rest is the chunk reader's.
- The JSON `raw` path of send, insert and import, and `decode_raw` holding its input beside its output, are as the log of responses-and-errors-hardening left them.
